# Hetu v0.2 — 设计规格（Design Spec）

> 日期：2026-08-14　状态：待评审（Draft for review）
> 上游：完整需求见 [../../requirements.md](../../requirements.md)；v0.1 范围与架构见 [../../mvp-v0.1.md](../../mvp-v0.1.md) 与 v0.1 设计 [./2026-08-08-hetu-mvp-design.md](./2026-08-08-hetu-mvp-design.md)。
> 本文件是 v0.2 的**实现规格**：在 v0.1（裸 Claude CLI 驱动）之上增量实现 **HITL 审批 + 通知 + Needs Attention/Unread**。

---

## 1. 目标与非目标

**目标（v0.2）**
- **HITL**：在 Hetu 内对 Claude 的工具调用做 approve / deny（透传 Claude 自身的权限决策）。
- **Needs Attention / Unread**：用户打开 Hetu 第一眼看到"哪些 Agent 在等我"。
- **通知**：后台 session 进入等待 / 完成 / 出错时，桌面通知找用户。
- 仍是 **Local + 单 CLI（Claude Code）**；命令式 CLI 为主。

**非目标（推后）**
- 自动审批策略 / allowlist / 规则引擎 → **v0.3**。
- defer / resume（人离开数小时的长等待）→ **v0.3**。
- Codex / OpenCode adapter → **v0.5**。
- Remote、Hetu App(GUI)、大量 session 分页/全文搜索 → 后续。

## 2. 关键决策

| 项 | 决策 | 理由 |
|---|---|---|
| 架构延续 | **继续裸 `claude` CLI 子进程 + stream-json**，不引入 Agent SDK | 官方对非 Python/TS 语言的原生建议就是"subprocess + `-p` + stream-json"；SDK 本身也是 spawn CLI 子进程，换 SDK = 多一层 sidecar + IPC，底下 CLI 不减、HITL 仍未真正绕开 hook |
| HITL 拦截点 | **`PermissionRequest` hook**（阻塞式 + daemon 回调） | 只在 Claude 自身认定"需要权限决策"时触发 → Hetu **零工具分类**，透传 Claude 的判断；读操作根本不触发，噪音天然合理 |
| 审批决策权 | **副作用操作一律问人，绝不自动放行**；读操作由 Claude 放行（不触发 hook） | 符合需求 §17/§22；hetu 不替用户在写/执行操作上点头 |
| 审批注入 | hetud 启动 claude 时经 `--settings` 注入一个 PermissionRequest hook，hook 命令 = `hetu __hook-permission` | 复用 hetu 二进制当 hook client；hook 经继承的 `HETU_SOCKET` 回连 daemon |
| 审批交互 | 命令式 `hetu approve\|deny` + `hetu watch` 流式就地审批 | SSH 友好 + 控制中心体验兼顾 |
| 审批等待上限 | **600s**（hook command 硬上限），超时 → 该工具按拒绝处理 | 官方限制；长等待走 v0.3 defer/resume |
| 通知通道 | 桌面通知（`notify-send` / `terminal-notifier`）；headless 不强推，靠 Needs Attention 视图 + watch | 不引入 webhook/外部依赖；保持 v0.2 聚焦 |
| 状态机 | 5 态 → 7 态（加 `WaitingForApproval` / `WaitingForInput`） | 需求 §10；Needs Attention 直接由状态派生 |
| Unread | `sessions` 加 `last_viewed_at`；`unread` 列复用（v0.1 已建） | 单 migration；查看即清 |

> **命门查证结论（已落地）**：headless `claude -p` 非交互；stream-json **不**吐权限事件、**不能**靠 stdin 回应；默认遇需权限工具 → 自动拒绝。唯一外部权限扩展点 = hook。详见 [附录 A](#附录-a命门查证依据)。

## 3. 总体架构（相对 v0.1 的增量）

```text
┌────────────────────────────────────────────────────────────────┐
│  CLI 薄客户端  cmd/hetu                                          │
│  + hetu approve|deny <id>   hetu watch <id>   (hidden) __hook-  │
│    permission                                                  │
└───────────────┬────────────────────────────────────────────────┘
                │ unix socket · JSON 帧
┌───────────────▼────────────────────────────────────────────────┐
│  hetu daemon                                                    │
│   SessionManager                                                │
│     ├─ liveSession.pump ── 事件扇出（现有）                      │
│     ├─ ApprovalBroker   ── pending 审批注册表 + Request/Resolve  │  ◄── 新增
│     └─ Notify           ── 状态跃迁 → 桌面通知                    │  ◄── 新增
│   Server                                                        │
│     ├─ RequestPermission(hook RPC，阻塞)  ─────────────────────┐ │  ◄── 新增
│     ├─ Approve/Deny/MarkRead/Watch handlers                   │ │  ◄── 新增
│     └─ （现有 List/Resume/Send/...）                           │ │
│   Store（SQLite）                                                │ │
│     sessions(+last_viewed_at) · session_events                 │ │
└────────────────────────────────────────────────────────────────┐ │
                │                                                │ │
                │ PermissionRequest hook 触发时：                 │ │
┌───────────────▼──────────────┐  阻塞回连（unix socket）          │ │
│  claude 子进程（hetud 拉起）   │ ◄──────────────────────────────┘ │
│   └─ hook: hetu __hook-permission  ◄── 读 stdin JSON             │
└──────────────────────────────────────────────────────────────────┘
```

审批是一条**独立于 stdin 的回路**：hook 进程（claude 的子进程）→ unix socket → daemon 的 `RequestPermission` handler（阻塞）→ 人决策 → 原路返回。`send`（发文本）仍走 stdin，两路彻底解耦。

## 4. HITL 机制详解（核心）

### 4.1 触发模型：透传 Claude 的权限决策

hetud 启动 claude 时注入 `PermissionRequest` hook（matcher `*`）。该 hook **只在 Claude 自己认定"此工具需要权限决策"时触发**——读操作（Read/Glob/Grep/LS）由 Claude 直接放行，**不触发 hook、不经 hetu**；有副作用的操作（Bash/Write/Edit/WebFetch…）触发 hook → hetu 透传给人。

> Hetu 不维护任何"哪些工具只读"的清单。边界 = Claude 自己的默认权限判定。

### 4.2 端到端回路

```text
1. claude 想调 Bash(npm install)，需权限
2. PermissionRequest hook 触发 → 执行 `hetu __hook-permission`
3. __hook-permission 读 stdin JSON{session_id, tool_name, tool_input, tool_use_id}
   ── 经继承的 HETU_SOCKET 拨号 daemon ──► RequestPermission RPC（阻塞）
4. daemon.SessionManager.RequestApproval：
   a. external_id(session_id) → hetu_id 解析
   b. 在 liveSession 注册 pending approval{tool_use_id, tool_name, tool_input, decisionChan}
   c. 广播 Event{Type:approval, ApprovalState:pending, ...} → 订阅者(hetu watch) 即时看到
   d. 状态置 WaitingForApproval（写 store + 广播 EventStatus）
   e. 阻塞在 decisionChan（带 ctx，TTL = hook 超时 - 安全余量）
5. 人决策：
   • hetu watch：屏上 y/n 就地回应
   • 命令式：hetu approve <id> [--tool <tool_use_id>]  /  hetu deny <id> [--reason ...]
6. daemon.ResolveApproval(hetu_id, tool_use_id, decision)：
   • decisionChan <- decision（解锁步骤 4e）
   • 广播 Event{Type:approval, ApprovalState:allowed|denied}
   • 状态回 Running（写 store）
7. RequestPermission RPC 返回 decision → __hook-permission 往 stdout 打决策 JSON
8. claude 收到 hook 决策 → 执行或中止工具 → 流继续
```

### 4.3 hook 注入

- hetud 在 `claudeArgs` 基础上追加 `--settings <hetu 管理的 settings 文件>`（路径如 `~/.hetu/claude-settings.json`），其内容：
  ```json
  {
    "hooks": {
      "PermissionRequest": [
        { "matcher": "*", "hooks": [
          { "type": "command", "command": "hetu __hook-permission", "timeout": 540 }
        ]}
      ]
    }
  }
  ```
- 同时给 claude 子进程显式注入 `HETU_SOCKET=<path>` 环境变量（hook 子进程继承，用于回连）。
- `timeout` 设为 540（留 60s 余量给回连往返，低于 600s 硬上限）。

### 4.4 超时与拒绝

- hook 超过 `timeout` 未返回 → 官方行为：工具"不阻塞、走默认权限流"，headless = **拒绝**。
- daemon 侧：`RequestApproval` 的 ctx 在 TTL 到期后取消 → 视为拒绝 → 广播 `Event{approval, state:timeout}` + 通知 → claude 收到拒绝。

### 4.5 多 pending 与消歧

- 一个 session 可能先后/并发多个 pending（Claude 并行 tool call 时）。每个 pending 以 `tool_use_id` 唯一标识。
- `hetu approve/deny` 无 `--tool` 时：若该 session 恰好 1 个 pending → 解它；>1 → 报错并列出 pending 让用户带 `--tool` 指定。
- `hetu watch` 遇 approval 事件时按事件内的 `tool_use_id` 就地回应，无歧义。

### 4.6 ApprovalBroker（daemon 内）

归属 `SessionManager`（复用 live map + broadcast），不另起包：

```go
type decision struct{ Allow bool; Reason string }

type pendingApproval struct {
    toolUseID, toolName, toolInput string
    ch   chan decision
    // createdAt 用于超时
}

// liveSession 增加：
//   pending map[string]*pendingApproval  // toolUseID -> pending
```

- `RequestApproval(ctx, hetuID, toolUseID, toolName, toolInput) (decision, error)`：注册 + 广播 + 阻塞。
- `ResolveApproval(hetuID, toolUseID string, d decision) (found bool)`：解锁 + 广播结果 + 清理。
- 并发安全：复用 `liveSession.mu`。

## 5. 统一状态模型（5 → 7 态）

```go
// internal/session/status.go  增补
StatusWaitingForApproval Status = "WaitingForApproval"
StatusWaitingForInput    Status = "WaitingForInput"   // 预留；Claude 无原生面，v0.2 主要走 Approval
```

**跃迁**：
- hook 触发（pending 注册）→ `WaitingForApproval`
- resolve allow → `Running`
- resolve deny → `Running`（agent 继续，只是该工具被否）
- session 结束 → `Completed` / `Error`（现有）
- 超时 → `Running`（按 deny 处理后同上）

**排序优先级**（`ListSessions` ORDER BY 重排）：
```
WaitingForApproval/WaitingForInput(0) → Error(1) → Running(2) → Completed(3) → Idle(4) → Unknown(5)
```
（v0.1 是 `Error→Running→Completed→Idle`，插入 Waiting 到最前。）

## 6. Unread / Needs Attention

### 6.1 Unread

- store：`sessions` 加列 `last_viewed_at INTEGER`（migration `002_viewed_at.sql`）。`unread` 列已存在（v0.1 建未用）。
- **写**：pump 每处理一条事件 → `unread=1`（已有 `last_event_at` 更新）。
- **清**：`MarkRead(hetuID)` → `last_viewed_at=now, unread=0`。
- 触发 MarkRead 的"查看"动作：`hetu session <id>`（详情）；`hetu watch <id>` attach 时也算。

### 6.2 Needs Attention

派生量，**不新增列**：
```
needs_attention := status IN ('WaitingForApproval','WaitingForInput','Error')
```

### 6.3 列表渲染

`hetu sessions` 默认按关注度分组（CLI output 层）：
```
Needs Attention
  [Claude] <title>   WaitingForApproval   (tool: Bash)
  [Claude] <title>   Error
Running
  [Claude] <title>   Running
Recent
  [Claude] <title>   Completed   ●(unread)
```
- `●` 标 unread。
- Project 行 badge = 该 project 下 `needs_attention OR unread` 的 session 计数（`hetu projects` 增强）。

## 7. 通知

- **触发**（pump 检测状态跃迁）：
  - 非 → `WaitingForApproval` / `WaitingForInput`
  - 非 → `Completed`
  - 非 → `Error`
- **通道**：`internal/notify` 包，接口 `Notifier.Notify(title, body, hint)`；实现：
  - Linux：`notify-send`（缺则跳过 + 日志）
  - macOS：`terminal-notifier`（有）→ 退 `osascript`（无则跳过）
- **headless / 无 GUI**：调用失败静默跳过（不报错给用户）；用户靠 Needs Attention 视图 + watch。
- **点击跳转**：CLI 无 GUI 跳转；body 里带 `hetu session <id>` 文本提示。真正 click-through 留到 App。
- **去重**：同一 session 同一状态短时间内只通知一次（pending→allowed 不重复通知 pending）。

## 9. 核心接口变更

### 9.1 agent.Event（新增 approval）

```go
// internal/agent/event.go
const EventApproval EventType = "approval"

type Event struct {
    Type        EventType      `json:"type"`
    Text        string         `json:"text,omitempty"`
    ToolName    string         `json:"tool_name,omitempty"`
    ToolJSON    string         `json:"tool_json,omitempty"`
    ToolUseID   string         `json:"tool_use_id,omitempty"`   // 新增（approval/tool）
    ApprovalState string       `json:"approval_state,omitempty"` // 新增：pending|allowed|denied|timeout
    Status      session.Status `json:"status,omitempty"`
    Err         string         `json:"err,omitempty"`
    Seq         int            `json:"seq"`
}
```

> `agent.Session` 接口**不加** `Approve` 方法：审批决策在 daemon 侧（ApprovalBroker）解决，不"推进"claudeSession 子进程。保持 Session 抽象聚焦于"流 + 发消息"。

### 9.2 API 类型（internal/api/types.go）

```go
type ApproveReq struct {
    ID        string `json:"id"`         // hetu_id 或前缀
    ToolUseID string `json:"tool_use_id,omitempty"` // 多 pending 时指定
    Allow     bool   `json:"allow"`      // true=approve,false=deny
    Reason    string `json:"reason,omitempty"`
}
type MarkReadReq struct{ ID string `json:"id"` }
type WatchReq struct{ ID string `json:"id"` }   // 复用 Subscribe 流，CLI 侧增强渲染

// hook 专用（阻塞）：
type PermissionRequestReq struct {
    SessionID  string `json:"session_id"`   // claude external_id
    ToolName   string `json:"tool_name"`
    ToolInput  string `json:"tool_input"`   // raw JSON
    ToolUseID  string `json:"tool_use_id"`
}
type PermissionRequestResp struct {
    Allow  bool   `json:"allow"`
    Reason string `json:"reason,omitempty"`
}
```

### 9.3 CLI（internal/cli）

新增文件：`approve.go`、`deny.go`（或合并 `approve.go` 含 deny）、`watch.go`、`hook.go`（隐藏命令 `__hook-permission`）。
- `hetu approve <id> [--tool <id>]` / `hetu deny <id> [--tool <id>] [--reason ...]`
- `hetu watch <id>`：订阅事件流（复用 client Subscribe），实时渲染 text/tool/status；遇 `approval` 事件 → 读 stdin 就地 `[y] approve / [n] deny / [s] skip`。
- `hetu __hook-permission`：读 stdin JSON → dial daemon `RequestPermission`（阻塞）→ 据 resp 打 hook 决策 JSON 到 stdout（决策 JSON 的确切形状见 spike，初稿见附录 B）。

### 9.4 daemon Server / SessionManager

- Server 新增 op：`approve`、`deny`（或合并 `approve` 带 Allow 布尔）、`mark_read`、`watch`、`permission_request`（hook）。
- `permission_request` handler：解析 `SessionID`(external) → `sm.RequestApproval(...)` 阻塞 → 返回 `PermissionRequestResp`。
- SessionManager：`RequestApproval` / `ResolveApproval`（见 §4.6）；pump 增加 approval 事件落盘 + 通知触发检测。

## 10. 关键命令数据流

| 命令 | 流程 |
|---|---|
| `hetu approve <id>` | client→`approve` RPC→`sm.ResolveApproval(allow)`→（若有 pending）解锁 hook→返回；无 pending→提示"无等待中的审批" |
| `hetu deny <id> --reason ...` | 同上，`ResolveApproval(deny{reason})` |
| `hetu watch <id>` | client→`watch`/`subscribe`→持续读事件→渲染；approval 事件就地交互→内部走 approve/deny RPC |
| `hetu session <id>` | 现有 + 若有 pending approval 一并展示 + `MarkRead` |
| `hetu sessions` | 现有 + 分组 + unread/attention 标记 |
| hook 回路 | claude→`hetu __hook-permission`→`permission_request` RPC（阻塞）→注册 pending+广播+Waiting→人决策→`ResolveApproval`→返回决策→hook stdout→claude |

## 11. 错误处理

- **hook 超时（>540s）**：按拒绝；通知 + 广播 timeout 事件；claude 收 deny。session 仍 Running，可继续。
- **daemon 重启 / session 未驱动**：hook 回连失败 → hook 进程退码 0 + 空 stdout（走默认流=拒绝），不挂死 claude；`approve` 对非驱动 session → 提示需先 resume。
- **`--settings` 注入失败**：hetud 启 claude 前校验 settings 文件可写；失败降级为"无 HITL"并日志警告（driven session 仍可跑，但副作用工具会被 claude 自动拒）。
- **notify 缺失/失败**：静默跳过 + 日志；不影响主流程。
- **多 pending 消歧**：`approve` 无 `--tool` 且 >1 pending → 报错 + 列出 pending tool_use_id。
- **context**：`RequestApproval` 带可取消 ctx；daemon 关闭时所有 pending 被取消（按拒绝）。

- unix socket / SQLite / 交叉编译：沿用 v0.1，无变化。

## 13. 测试策略

接口优先 → HITL 回路用 fake 驱动测，不依赖真 claude。

- **ApprovalBroker**：`RequestApproval`/`ResolveApproval`/超时/并发/多 pending——纯单测（fake liveSession）。
- **状态机 + 排序 + Unread 规则**：store 单测（临时 SQLite），含 `last_viewed_at`/`MarkRead`。
- **通知触发**：喂事件序列 → 断言只在跃迁点触发、去重正确（fake Notifier）。
- **hook client 往返**：内嵌 fake daemon，`hetu __hook-permission` 读 fixture stdin → 断言阻塞 + 返回决策 JSON。
- **CLI**：`approve`/`deny`/`watch` 的 golden + 往返（fake daemon 模拟 approval 事件）。
- **（gated e2e）**：真 `claude -p`，发一条会触发 Bash 的 prompt，确认 hook 闭环、approve 后继续。需 API key，非阻塞。

## 14. Spike（实现前必做，gating）

实现第一步是 **spike**，确认 hook 路径可走通；任一项不成立则回退方案见下：

1. **PermissionRequest 在 `-p` headless 下确实触发**，且输入 JSON 含 `tool_name/tool_input/tool_use_id/session_id`。
2. **PermissionRequest 的决策输出 JSON schema**（allow/deny 的确切字段）——官方未文档化，需实测/反查（见附录 B）。
3. **`--settings <file>` 注入**：hetud 驱动时 hook 正常触发；settings 与用户自有 settings 的合并行为。
4. **headless 默认行为**：无 hook 时副作用工具确实被自动拒（确认 hook 不可或缺）。

**回退**：若 #1/#2 不成立 → 改用 `PreToolUse`（决策输出 `permissionDecision:allow|deny` 已文档化），代价是 PreToolUse 对**每个** tool 触发，hetu 需最小分类（只读放行/副作用问人）——届时回到用户重新确认边界。若 #3 不成立 → 探索 `CLAUDE_CONFIG_DIR` / 项目 `.claude/settings.local.json`。

## 15. v0.2 限制与未来

**限制（需如实告知用户）**
- 审批等待 ≤600s，超时按拒绝；"人离开数小时"不支持（→ v0.3 defer/resume）。
- 无自动审批/allowlist（→ v0.3）。
- 仅 Claude Code、仅 Local。
- 通知点击=文本提示，无 GUI 跳转（→ App）。

**未来**
- v0.3：auto-allowlist / 策略引擎；defer+resume 长等待；或反查 SDK 用的未公开 stdio 权限协议（可破 600s 上限）。
- v0.5：Codex（app-server JSON-RPC）、OpenCode（HTTP+SSE）——各自一个 adapter；HITL 走各自原生面。
- Remote、App、全文搜索/分页。

## 附录 A：命门查证依据

- headless `claude -p` 非交互；stream-json 不吐权限事件、不可经 stdin 回应；默认自动拒绝（官方 hook 文档 + 行为）。
- hook 是唯一外部权限扩展点；`PermissionRequest` 仅在 Claude 需决策时触发；command hook 上限 600s，超时不阻塞→默认流（headless=拒）。
- Agent SDK（Python/TS）本身也 spawn `claude` CLI 子进程经 stdio 通信——换 SDK 不消除 CLI 子进程，对 Go 只增加 sidecar+IPC，非更优。官方对非 Python/TS 的建议即"subprocess + `-p` + stream-json"（hetu 现状）。

## 附录 B：PermissionRequest 决策 JSON（待 spike 确认）

官方未文档化 PermissionRequest 的决策输出 schema（已知：exit code 2 对它**不**生效，须用 JSON `decision` 对象）。spike 待确认形如：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PermissionRequest",
    "decision": { "behavior": "allow", "updatedInput": {} }
  }
}
```

`behavior` 取 `allow` / `deny`。spike #2 确认字段名后，`hetu __hook-permission` 据此拼装 stdout。若实测与此不符，以实测为准并更新本附录。
